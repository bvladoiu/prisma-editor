# Component Coding Standards for Prisma Editor

## 1. Introduction

This document outlines the consistent coding standards for components in the `prisma.editor.component` package and page classes in `prisma.editor.pages`. Adhering to these standards will improve code readability, maintainability, and facilitate the generation of both the editor's interactive live preview and the static client-side HTML export.

These standards are applicable to all coding agents working on the Prisma Editor project.

## 2. Component Categories

Components are categorized based on their role and how they interact with the DOM:

*   **Top-Level Components:** These components represent distinct structural elements on a page (e.g., `Section`, `Hero`, `ArticleCard`, `NavigationMenu`) or editor UI elements (`Drawer`, `FloatingActionButton`). They are responsible for managing their own root `HTMLElement` in the editor's live view and generating their own HTML string for static export (if applicable).
*   **Embeddable DSL Components:** These components are smaller building blocks that provide DSL functions to be embedded *within* the HTML structure created by Top-Level Components (e.g., `Icon`, `Image`, and potentially a `Text` component). They do not manage their own `HTMLElement` directly but contribute to the HTML generated by their parent components using the `kotlinx.html` DSL.

## 3. Standards for Top-Level Components

Top-Level Components **must** adhere to the following standards:

### 3.1. Data Handling

*   Component data should be stored in class properties (`var` or `val` as appropriate).
*   Initial data can be passed via the constructor.
*   Data updates must be handled by a `set(data: dynamic)` method.

### 3.2. HTML Generation

*   **`buildEditorDom(): HTMLElement`**:
    *   **Purpose:** Generates the DOM structure for the editor's interactive live view.
    *   **Implementation:** Must use `kotlinx.html.dom`.
    *   **Content:** May include editor-specific elements, attributes (e.g., `contenteditable`, `data-component-tag`), and event handlers (e.g., `onClickFunction` calling `@JsName` functions).
*   **`buildStaticHtml(): String`**:
    *   **Purpose:** Generates the clean, static HTML string intended for the final client-side page export.
    *   **Implementation:** Must use `kotlinx.html.stream.createHTML`.
    *   **Content:** **Must not** include any editor-specific elements, attributes, or JavaScript event handlers. Only contain the HTML relevant to the static page.
    *   **Applicability:** Components intended for static page content must have this method. Editor-only components may omit it.

### 3.3. CSS Rule Definition

*   CSS rules must be defined in a `cssRules()` companion object method returning `List<CssRuleDefinition>`.
*   Use attribute selectors (e.g., `[data-component-tag="hero"]`) for styling the component's root element.

### 3.4. Rendering and Lifecycle (for components managed in the live editor DOM)

For Top-Level Components that are rendered and updated in the live editor DOM, the following methods must be implemented consistently:

*   **`renderTo(parentElement: HTMLElement)`**:
    *   **Purpose:** Appends the component's `buildEditorDom()` output to a parent element and stores a reference to the created root element.
*   **`refreshDom()`**:
    *   **Purpose:** Replaces the component's current `rootElement` in the DOM with a new element generated by `buildEditorDom()`. This should be called after data is updated via `set()`.
*   **`detach()`**:
    *   **Purpose:** Removes the component's `rootElement` from the DOM.

### 3.5. Core Methods

Top-Level Components should include the following methods:

*   `commit()`: Placeholder for saving component data.
*   `load()`: Placeholder for loading component data.
*   `set(data: dynamic)`: Updates component properties and calls `refreshDom()`.
*   `refreshDom()`: Updates the component's DOM representation in the editor. (Required for components managed in the live DOM).

### 3.6. Editor-Specific Functionality

*   Editor-specific behavior triggered by user interaction (e.g., adding/deleting items, calling editor commands) should be implemented in companion object functions annotated with `@JsName`.
*   These `@JsName` functions are then called from event handlers (like `onClickFunction`) placed within the `buildEditorDom()` method.

## 4. Standards for Embeddable DSL Components

Embeddable DSL Components **must** adhere to the following standards:

### 4.1. HTML Generation

*   Provide one or more extension functions on `FlowContent` (or other appropriate `kotlinx.html` building blocks) that define how to render the component's HTML using the `kotlinx.html` DSL.
*   These functions should accept necessary parameters for data and styling.
*   They **must not** include editor-specific elements or attributes, as their purpose is to contribute to the static HTML structure.
*   **Example (`Icon`):**
```
kotlin
    fun FlowContent.icon(name: String, classes: Set<String> = emptySet()) {
        span(classes = classes.joinToString(" ")) {
            attributes[Typography.ICON] = "" // Example attribute
            +name
        }
    }
    
```
*   **Example (`Image`):**
```
kotlin
    fun FlowContent.image(src: String, alt: String = "", width: String = "auto", height: String = "auto", classes: Set<String> = emptySet()) {
        img(src = src, alt = alt) {
            classes = classes.joinToString(" ")
            attributes["width"] = width
            attributes["height"] = height
        }
    }
    
```
### 4.2. No `HTMLElement` Management

*   These components **must not** have a `rootElement` property.
*   They **must not** have methods like `renderTo`, `refreshDom`, or `detach`. Their DOM is managed by the Top-Level Component they are embedded within.

### 4.3. No Core Methods

*   Embeddable DSL Components typically do not require `commit()`, `load()`, or `set()` methods. Their data is usually provided via the DSL function parameters.

### 4.4. CSS Rule Definition

*   CSS rules for styling the embedded elements should be defined in a `cssRules()` companion object method returning `List<CssRuleDefinition>`, similar to Top-Level Components.

## 5. Standards for Page Classes

Page classes (`Page` and its subclasses) define the structure and content of a page and **must** adhere to the following standards:

### 5.1. HTML Generation

*   **`createEditorPage(): HTMLElement`**:
    *   **Purpose:** Builds the full DOM for the editor's interactive view of the page.
    *   **Implementation:** Must use `kotlinx.html.dom`.
    *   **Content:** Calls `buildEditorDom()` on the Top-Level Components it contains and includes editor UI components (like the `Drawer`).
*   **`toStaticHtmlString(pages: List<Page>): String`**:
    *   **Purpose:** Generates the complete static HTML string for the client-side page export.
    *   **Implementation:** Must use `kotlinx.html.stream.createHTML`.
    *   **Content:** Calls `buildStaticHtml()` on the Top-Level Components that are part of the static content and excludes editor UI components. It should also include necessary HTML boilerplate (`<!DOCTYPE html>`, `<html>`, `<head>`, `<body>`), linking CSS rules (collected from `cssRules()` of all included components and the page itself) and scripts.

### 5.2. Data Handling

*   Manage page-level data (e.g., page tag, name, component data structure) using properties.
*   Include `commit()`, `load()`, and `set()` methods for managing page data.

### 5.3. Resource Inclusion

*   The `toStaticHtmlString()` method (or a utility it calls) is responsible for collecting all necessary CSS rules (from `cssRules()` of included components and the page) and JavaScript references, and including them correctly in the static HTML output.

## 6. Consistency Checklist

Coding agents should use the following checklist during development and code reviews:

*   [ ] Is the component correctly categorized as Top-Level or Embeddable DSL?
*   [ ] Does the component adhere to the standards for its category?
*   **For Top-Level Components:**
    *   [ ] Are `buildEditorDom(): HTMLElement` and (if applicable) `buildStaticHtml(): String` methods present?
    *   [ ] Does `buildEditorDom()` use `kotlinx.html.dom`?
    *   [ ] Does `buildStaticHtml()` use `kotlinx.html.stream.createHTML`?
    *   [ ] Is `buildStaticHtml()` free of editor-specific logic and elements?
    *   [ ] Are rendering/lifecycle methods (`renderTo`, `refreshDom`, `detach`) implemented consistently if the component is managed in the live DOM?
    *   [ ] Are `commit()`, `load()`, and `set()` methods present?
*   **For Embeddable DSL Components:**
    *   [ ] Is/Are `FlowContent` (or appropriate) extension function(s) provided for rendering?
    *   [ ] Does it lack `rootElement`, `renderTo`, `refreshDom`, `detach`, `commit`, `load`, and `set` methods?
*   **For All Components:**
    *   [ ] Are CSS rules defined in the `cssRules()` companion object method?
*   **For Page Classes:**
    *   [ ] Are `createEditorPage(): HTMLElement` and `toStaticHtmlString(pages: List<Page>): String` methods present?
    *   [ ] Does `createEditorPage()` use `kotlinx.html.dom` and call `buildEditorDom()` on contained components?
    *   [ ] Does `toStaticHtmlString()` use `kotlinx.html.stream.createHTML` and call `buildStaticHtml()` on relevant components?
    *   [ ] Does `toStaticHtmlString()` handle resource inclusion (CSS, JS)?

## 7. Refactoring Existing Code

All existing components and page classes must be refactored to comply with these standards. This should be done incrementally, component by component. Prioritize refactoring based on component category and usage.
